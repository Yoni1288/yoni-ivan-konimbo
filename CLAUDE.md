# CLAUDE.md — Project Guidelines

## Project Constraints (README — these override everything below)

- **Do not modify:** `mock-data/`, `src/app/api/`, `src/types/product.ts`. Adding new files, routes, or extended types is fine.
  - The one exception: the `/map-s3-images` command (`scripts/map-s3-images.ts`) may change the `thumbnail` and `images` fields of `mock-data/products.json`. Nothing else may change `mock-data/`.
- `pnpm install && pnpm dev` must work from a clean clone. A `postinstall` script runs `prisma generate`; the one-time database setup is in section 10.
- **Over-engineering is not a plus.** Prefer clean, focused work over feature count. The task is scoped at about 6 hours.

## Project

A take-home "Product Quick View" storefront feature:

- Product grid with search and filters at `/products`
- Quick View modal (variant selector, price and stock per variant)
- Client-side cart drawer and a checkout form with validation that only shows a success message (no order backend)

## Tech Stack

- **App:** Next.js 16 (App Router, Turbopack), React 19. One app; there is no separate backend or frontend.
- **Backend:** Next.js API routes in `src/app/api/products/`, which read static JSON from `mock-data/products.json`
- **Language:** TypeScript 5.9 (`strict`)
- **Styling:** Tailwind CSS 4
- **Validation:** Zod 4
- **ORM:** Prisma (PostgreSQL)
- **Server state:** TanStack Query
- **Client state:** Zustand (cart only)
- **Forms:** React Hook Form + `@hookform/resolvers` (Zod)
- **Icons:** lucide-react
- **Package manager:** pnpm 10.28.2, Node 22+
- **Infrastructure:** Docker Compose (PostgreSQL, accessed through Prisma; the app can also run in Compose)

## 1. Clean Procedural Code

- Write code as a clear, top-to-bottom sequence of steps.
- One function = one responsibility. Keep functions short and readable.
- Prefer early returns over deep nesting.
- Use descriptive names for variables and functions so the code reads like a procedure.
- Avoid clever one-liners, hidden side effects, and unnecessary abstractions.

### Length checks

- Check for empty or non-empty arrays and strings with truthiness, not explicit comparisons. This is enforced by `no-restricted-syntax` in the ESLint config.
- ✅ `if (!items.length) return;` / `if (items.length) renderList(items);`
- ❌ `if (items.length === 0) return;` / `if (items.length > 0) renderList(items);`
- Compare explicitly only when checking a specific count (e.g. `items.length === 1`).

## 2. Comments

- Do **not** add comments to simple or self-explanatory code.
- Only comment when explaining _why_ something non-obvious is done (business rule, workaround, edge case).
- Never write comments that restate what the code does.

## 3. TypeScript Types Everywhere

- Every variable, parameter, return value, API response, and component prop must be typed.
- `any` is forbidden. Use `unknown` and narrow it when the type is truly unknown.
- Define types in dedicated files (e.g. `*.types.ts`).
- `src/types/product.ts` must not be modified. Extend its types in feature type files instead.
- Keep `strict: true` in `tsconfig.json`.

## 4. Thin Route Files

- Files in `src/app/` (`page.tsx`, `layout.tsx`, `route.ts`) contain **only the core flow**.
- UI and logic live in `src/features/`; reusable logic lives in `src/shared/`.
- If logic is used more than once, extract it into a function.

```tsx
// src/app/products/page.tsx
const ProductsPage = (): React.JSX.Element => {
  return <ProductCatalog />
}

export default ProductsPage
```

```ts
// A new route handler (never edit the existing ones in src/app/api/)
export const GET = withErrorHandling(async (request: Request): Promise<Response> => {
  const query = parseSearchParams(request, searchQuerySchema)
  return Response.json(await findProducts(query))
})
```

## 6. Global Error Handling Over Multiple try/catch

- Prefer **one central error handler per layer** over scattered `try/catch` blocks.
- **Route handlers:** wrap every new handler in the shared `withErrorHandling` helper (`src/shared/errors/`).
- **Client API layer:** all `fetch` calls go through one shared client in `src/shared/api/` that handles errors in one place.
- **UI:** use `src/app/error.tsx` and `src/app/global-error.tsx` as error boundaries.
- Only use a local `try/catch` when you must recover or add specific context at that point — then rethrow a known error.

## 7. Input Validation With Zod

- All input must be validated using **Zod** (never hand-written validation).
- New route handlers: validate request body, params, and search params with Zod.
- Client: validate forms (e.g. checkout) and API responses with Zod schemas.
- Derive TypeScript types from schemas (`z.infer<typeof schema>`) to avoid duplication.

## 8. Never Expose Unknown Exceptions to the Client

- The client must only receive known, safe error responses.
- Unknown errors are logged on the server and returned as a generic message:

```json
{ "statusCode": 500, "message": "Internal server error" }
```

- Never send stack traces or internal details to the client.

## 9. Every Error Must Be Handled

- No error may be silently swallowed.
- Every caught error must be passed to the error-reporting placeholder:

```ts
sendError(log)
```

- `sendError` is a **placeholder** until a real error system exists. It lives in `src/shared/errors/` so it can be replaced in one place later.
- `withErrorHandling`, the client API layer, and the error boundaries must all call `sendError`.

```ts
// src/shared/errors/with-error-handling.ts
export const withErrorHandling = <TContext>(handler: (request: Request, context: TContext) => Promise<Response>) => {
  return async (request: Request, context: TContext): Promise<Response> => {
    try {
      return await handler(request, context)
    } catch (error) {
      sendError({ error })

      if (error instanceof HttpError) {
        return Response.json({ statusCode: error.statusCode, message: error.message }, { status: error.statusCode })
      }

      return Response.json({ statusCode: 500, message: "Internal server error" }, { status: 500 })
    }
  }
}
```

- A single `docker-compose.yml` at the project root defines the services and volumes.
- All config comes from environment variables via `.env` (commit `.env.example`, never the real `.env`).
- Persist PostgreSQL data with a named volume and keep the `pg_isready` healthcheck.
- The app on the host connects via `localhost:5432`. If the app ever runs inside Compose, it must use the service name `postgres` instead.

## 11. Always Responsive (Mobile First)

- Every page and component must work on mobile phones, tablets, and desktop.
- Design mobile first: base Tailwind classes target small screens, and `sm:` / `md:` / `lg:` prefixes add larger layouts.
- Test every UI change at phone width (at least 360px) before it is considered done.
- No horizontal scrolling on any screen size.
- Use flexible layouts (Flexbox / Grid) and relative units instead of fixed pixel widths.
- Touch targets (buttons, links, inputs) must be at least 44×44px.
- Images and media must scale with their container.
- Modals and drawers (Quick View, cart) must fit and scroll within a phone screen.
- Next.js adds the viewport meta tag by default; don't remove it (use `export const viewport` if it needs changing).
- Use Tailwind's breakpoints only (customize them once in the CSS `@theme` if needed); never hardcode breakpoint values in components.

## 12. Every API Route Has a Test

- Every API route must have **at least one test case** proving the route works (happy path).
- A new route is not done until its test exists and passes.
- Use **Vitest** (not installed yet; add it as a dev dependency with the first test). Import the route handler and call it directly with a `NextRequest` (the existing handlers read `request.nextUrl`); check the status code and response body.
- Tests are new files; never modify files in `src/app/api/` to make them testable.
- Route tests that hit the database use a separate test database (`DATABASE_URL` from `.env.test`), never the dev database.
- Error-case tests (validation failure, not found) are encouraged but not required yet.

```ts
import { NextRequest } from "next/server"
import { describe, expect, it } from "vitest"
import { GET } from "@/app/api/products/route"

describe("GET /api/products", () => {
  it("returns products", async () => {
    const response = await GET(new NextRequest("http://localhost/api/products"))
    const body: unknown = await response.json()

    expect(response.status).toBe(200)
    expect(body).toHaveProperty("products")
  })
})
```

## 13. State Management — Each State in the Simplest Place That Works

Classify state before writing it, then put it in exactly one place:

| State                                     | Lives in                                           | Tool                                 |
| ----------------------------------------- | -------------------------------------------------- | ------------------------------------ |
| Search, filters, pagination               | URL search params (`?q=&collection=&tag=&offset=`) | `useSearchParams` + `router.replace` |
| Product data (server state)               | Query cache                                        | TanStack Query                       |
| Quick View open product, selected options | Component                                          | `useState`                           |
| Cart items, cart drawer open              | Global client store                                | Zustand                              |
| Checkout form                             | Form state                                         | React Hook Form + Zod                |

- **Do not add** Redux, Jotai, extra Context stores, or any other state library.
- **Never duplicate state.** If a value can be computed from other state, compute it (`useMemo` or a selector). Never store it.

### URL state (search & filters)

- The URL is the single source of truth for search, filters, and pagination. Never mirror them in `useState` or Zustand.
- Read and write them through one hook (`useProductFilters` in `src/features/products/hooks/`).
- Debounce the search input (~300ms), update with `router.replace` (not `push`) inside `startTransition`, and reset `offset` to 0 when a filter changes.
- Wrap the component that calls `useSearchParams` in `<Suspense>`, or `next build` fails for the page.

### Server state (TanStack Query)

- All product fetching goes through TanStack Query. Never fetch in `useEffect`.
- Never fetch our own `/api` routes from Server Components. Fetching happens on the client.
- Query functions call the shared API client (`src/shared/api/`) and validate the response with a Zod schema.
- Define query keys in one factory per feature, derived from the URL params:

```ts
export const productKeys = {
  all: ["products"] as const,
  list: (filters: ProductFilters) => [...productKeys.all, "list", filters] as const,
  detail: (id: string) => [...productKeys.all, "detail", id] as const,
}
```

- Use `placeholderData: keepPreviousData` on the list so the grid doesn't flash while filtering.
- Every query must render loading, error, and empty states.
- Report query errors once, globally, in the `QueryClient` config. Don't add `onError` to each query:

```ts
new QueryClient({
  queryCache: new QueryCache({ onError: (error: Error) => sendError({ error }) }),
})
```

- Create the `QueryClient` inside `useState` in `src/app/providers.tsx` so it isn't shared between requests.
- Pass the product from the list to Quick View. The list payload already includes full variants and options, so don't fetch `/api/products/:id` for it.

### Local state (Quick View)

- Store only `selectedOptions: Record<string, string>`. Derive the selected variant, its price, and its stock from it.
- Variants carry no option values, only a `title` like `"750ml - Black"` whose parts follow the order of `product.options`. Match a variant by splitting its title on `" - "` and comparing the first N parts (N = number of options) to the selection. Some titles have extra parts (e.g. `prod_14`: option `Size`, title `"EU 42 - Black"`), and some combinations have no variant (e.g. `prod_20` has no `King - Slate`).
- Preselect the first in-stock variant when the modal opens (the first variant if none are in stock).
- Disable (don't hide) option values that have no variant, or no in-stock variant, for the current selection.

### Global state (Cart — Zustand)

- One store: `src/features/cart/store/cart.store.ts`. Components only read it through selectors, never the whole store:

```ts
const itemCount: number = useCartStore((state) => selectCartItemCount(state))
```

- Cart lines are keyed by `variantId`. Adding an existing variant increases its quantity instead of adding a new line.
- Store a snapshot per line: `variantId`, `productId`, `title`, `variantTitle`, `thumbnail`, `unitPrice`, `currencyCode`, `inventoryQuantity`, `quantity`.
- Totals and counts are selectors, never stored values.
- Clamp quantity to the variant's `inventory_quantity`, and never add a variant with `inventory_quantity` 0. Store `inventoryQuantity` in the line snapshot so the cart can clamp without refetching.
- Persist with the `persist` middleware and use `partialize` to save only `items`, never UI state like `isOpen`.
- Prevent hydration mismatches: use `skipHydration: true` and call `useCartStore.persist.rehydrate()` in an effect, so the server and first client render agree (empty cart).
- Actions live inside the store (`addItem`, `removeItem`, `clearCart`, `openCart`, `closeCart`). Components never build new cart arrays themselves.
- Clear the cart only after the checkout success state has rendered.

### Form state (Checkout)

- Use React Hook Form with `zodResolver(checkoutSchema)`. The schema lives in `src/features/checkout/checkout.schemas.ts` and the form type is `z.infer<typeof checkoutSchema>`.
- Validate on blur, re-validate on change (`mode: 'onTouched'`).
- Show an error message under each invalid field and link it with `aria-describedby`.
- Disable submit while submitting and block checkout when the cart is empty.

### Money

- Prices in `mock-data/` are in **minor units** (agorot): amounts run 11900–149900 ILS and are all multiples of 100, so `29900` means ₪299.00. Divide by 100 before formatting. This differs from Medusa v2, which uses major units.
- Format all prices through one shared helper using `Intl.NumberFormat` and the product's currency code.

## 14. Formatting

- Maximum line length is 200 characters, enforced by Prettier (`printWidth: 200` in `.prettierrc`).
- Run `pnpm format` before committing. Never hand-format against the Prettier config.
- Do not use ESLint's `max-len` rule; Prettier owns line length.

## 15. Code Style

- Always define React components as arrow functions assigned to a `const`, never with the `function` keyword.
- Keep the explicit return type on the arrow function.
- Enforced by ESLint: `react/function-component-definition` (arrow functions for named and unnamed components) and `func-style: "expression"`.
- Run the lint script after making changes and fix any errors.

✅ Correct:

```tsx
const StockBadge = ({ status }: { status: StockStatus }): React.JSX.Element | null => {
  // ...
}
```

❌ Wrong:

```tsx
function StockBadge({ status }: { status: StockStatus }): React.JSX.Element | null {
  // ...
}
```

## 16. Styling

The project uses **Tailwind CSS v4**: there is no `tailwind.config`; theme tokens live in the `@theme` block of `src/app/globals.css`.

- Use Tailwind utility classes only. No inline `style`, CSS modules, or `@apply` for component styles.
- Use theme tokens (colors, spacing, font sizes). Don't use arbitrary values like `text-[11px]`. If a value is missing, add a token to `@theme` in `src/app/globals.css` (e.g. `--text-2xs`, `--color-swatch-*`, `--grid-template-columns-sidebar`) and mention it.
- Values that come from data (e.g. a swatch color) map to full class names built from tokens (`bg-swatch-black`), never to `style`. Write class names out in full so Tailwind can find them.
- Use `cn()` from `@/shared/utils/cn` (clsx + tailwind-merge) to combine or add conditional classes. Never build class strings with template literals.
- Use `cva` from `class-variance-authority` for components with visual variants (e.g. `stockBadge`, `pageButton`, `categoryButton`). Don't branch between full class strings.
- Mobile first: base classes target mobile, then `sm:` / `md:` / `lg:` add larger layouts (see section 11).
- `prettier-plugin-tailwindcss` sorts class names on `pnpm format`, including inside `cn()` and `cva()`. Don't sort them by hand.

```tsx
// ✅
const stockBadge = cva("rounded-full px-2.5 py-1 text-2xs font-medium", {
  variants: { status: { "low-stock": "bg-badge-low text-ink", "sold-out": "bg-ink text-white" } },
})
<span className={stockBadge({ status })} />
<div className={cn("rounded-xl", tileClass)} />

// ❌
<span className={status === "sold-out" ? "rounded-full bg-ink text-[11px]" : "rounded-full bg-badge-low text-[11px]"} />
<li style={{ backgroundColor: swatch.hex }} />
```

## 17. Environment Variables

### Typed, validated env

- Never read `process.env` directly in app code. Import the typed `env` object instead.
- Server env lives in `src/shared/config/env.server.ts`: a Zod schema parsed once at import time, so the app fails at startup with a clear error if a variable is missing or invalid. Derive the type with `z.infer`.
- The file starts with `import "server-only"` so it can never be bundled into a client component. Install `server-only` as a dependency so TypeScript and Vitest can resolve it.
- Client env (only if ever needed) lives in `src/shared/config/env.client.ts`. Browser variables must be prefixed `NEXT_PUBLIC_` and referenced literally (`process.env.NEXT_PUBLIC_X`), because Next.js only inlines literal references at build time.
- Never put secrets in `NEXT_PUBLIC_` variables. They are shipped to the browser.
- Every new variable is added to the Zod schema and to `.env.example` in the same change.
- No env library (e.g. `@t3-oss/env-nextjs`). A small Zod module is enough.

```ts
// src/shared/config/env.server.ts
import "server-only"
import { z } from "zod"

const serverEnvSchema = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
  DATABASE_URL: z.url(),
})

export type ServerEnv = z.infer<typeof serverEnvSchema>

export const env: ServerEnv = serverEnvSchema.parse(process.env)
```

```ts
// ✅
import { env } from "@/shared/config/env.server"
const adapter = new PrismaPg({ connectionString: env.DATABASE_URL })

// ❌
const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL })
const apiUrl = process.env[`NEXT_PUBLIC_${name}`] // not inlined, undefined in the browser
```

### Files

| File           | Committed                      | Contains                                                          |
| -------------- | ------------------------------ | ----------------------------------------------------------------- |
| `.env.example` | Yes                            | Placeholder values. The documentation of every variable.          |
| `.env`         | No (gitignored)                | Local values. Read by Next.js, the Prisma CLI and Docker Compose. |
| `.env.test`    | Only if it contains no secrets | The test database URL (section 12).                               |

- Keep all local values in `.env`, not `.env.local`. Prisma and Docker Compose don't read `.env.local`.
- Production secrets come from the hosting platform or a secrets manager, never from committed files.

### Exceptions and tooling

- Don't import `dotenv` in app code; Next.js 16 loads `.env` files itself. `dotenv/config` is imported only in `prisma.config.ts`.
- `prisma.config.ts` and `prisma/seed.ts` run outside Next.js, so they read `process.env` directly. They must not import the `server-only` env module, directly or through another import (this includes `@/shared/db/prisma`). The seed creates its own `PrismaClient`.
- `prisma.config.ts` reads `DATABASE_URL` leniently (`process.env.DATABASE_URL ?? ""`), not with Prisma's `env()` helper. `env()` throws when the variable is missing, which would break `prisma generate` in `postinstall` on a clean clone (section 10).
- Vitest does not load `.env.test` automatically. Call `process.loadEnvFile(".env.test")` (built into Node 22+) at the top of `vitest.config.ts`, not in a `setupFiles` file. `setupFiles` runs after `globalSetup`, so the migrate and seed there would hit the dev database from `.env`.
- `server-only` throws outside a React Server Component build, so `vitest.config.ts` aliases it to an empty module. Otherwise any route test that imports `env.server.ts` (e.g. through `@/shared/db/prisma`) fails.

## Database (Prisma + PostgreSQL)

### Version and setup

- Use **Prisma 7** (`prisma@7`, `@prisma/client@7`, `@prisma/adapter-pg@7`). Pin the major: npm's `latest` tag points to the Prisma 8 release candidate, which is a rewrite with a different setup.
- Generator: `provider = "prisma-client"` with `output = "../src/generated/prisma"` (required in Prisma 7). Import the client from `@/generated/prisma/client`; gitignore the generated folder.
- `prisma.config.ts` at the project root holds the schema path, `migrations.path`, `migrations.seed` (`tsx prisma/seed.ts`) and `datasource.url`. The Prisma 7 CLI doesn't load `.env` itself, so the config imports `dotenv/config`.
- PostgreSQL connects through the `@prisma/adapter-pg` driver adapter (required in Prisma 7).
- `DATABASE_URL` comes from `.env` and is listed in `.env.example`.

### Access rules

- All database access goes through Prisma. Raw SQL is forbidden, including `$queryRawUnsafe` and `$executeRawUnsafe`.
- If raw SQL is ever unavoidable, use the tagged `$queryRaw` template (it parameterizes values) and explain why in a comment.
- One Prisma client instance in app code, exported from `src/shared/db/prisma.ts`, cached on `globalThis` in development so hot reload doesn't open new connections. `prisma/seed.ts` is the exception: it runs outside Next.js and creates its own client (section 17).
- Prisma is only used in server code (route handlers, server components, repositories). Never import it in a client component.
- Prisma calls live only in repository files (`src/features/<feature>/repositories/`). Route handlers and components call repository functions, never Prisma directly.
- Repositories return types derived from Prisma (e.g. `Prisma.ProductGetPayload<...>`) or a mapped domain type. No hand-written duplicate row types.
- Use `select` to return only the fields needed; don't return whole rows by default.

```ts
// src/shared/db/prisma.ts
import { PrismaPg } from "@prisma/adapter-pg"
import { PrismaClient } from "@/generated/prisma/client"
import { env } from "@/shared/config/env.server"

const globalForPrisma = globalThis as typeof globalThis & { prisma?: PrismaClient }

const createPrismaClient = (): PrismaClient => {
  const adapter = new PrismaPg({ connectionString: env.DATABASE_URL })
  return new PrismaClient({ adapter })
}

export const prisma: PrismaClient = globalForPrisma.prisma ?? createPrismaClient()

// Reuse one client across dev hot reloads instead of opening a new connection pool per reload.
if (env.NODE_ENV !== "production") {
  globalForPrisma.prisma = prisma
}
```

```ts
// src/features/products/repositories/products.repository.ts
import type { Prisma } from "@/generated/prisma/client"
import { prisma } from "@/shared/db/prisma"

const productSummarySelect = {
  id: true,
  title: true,
  thumbnail: true,
} satisfies Prisma.ProductSelect

export type ProductSummary = Prisma.ProductGetPayload<{ select: typeof productSummarySelect }>

export const findProductSummaryById = async (id: string): Promise<ProductSummary | null> => {
  return prisma.product.findUnique({ where: { id }, select: productSummarySelect })
}
```

### Migrations and seed

- Schema changes happen only in `prisma/schema.prisma`, followed by `pnpm prisma migrate dev --name <description>`.
- Never edit applied migration files or change the database by hand. Commit migrations.
- Seed data lives in `prisma/seed.ts` and runs with `pnpm prisma db seed`.
- In Prisma 7, `migrate dev` no longer runs `prisma generate` or the seed; run them explicitly when needed.

### Errors

- Map known Prisma errors (`Prisma.PrismaClientKnownRequestError`) to `HttpError` inside the error handling layer, so section 8 still holds:
  - `P2025` (record not found) → 404
  - `P2002` (unique constraint violation) → 409
- Any other Prisma error is an unknown error: report it with `sendError` and return the generic 500. No Prisma error details reach the client.
